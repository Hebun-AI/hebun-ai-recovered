# 06 — Operating Boundaries

## Purpose

The Operating Boundaries define **what the Enterprise Operating Model does not do**. The Operating Model is powerful because it is narrow: it operates the organization and nothing else. This document draws the lines that keep it from drifting into execution, reasoning, orchestration, governance redefinition, or authority bypass.

## Architectural role

Where the operating principles ([01](01-operating-principles.md)) state what operation must obey, the boundaries state what it must refuse. Together they fence the Operating Model into its single concern — continuous organizational operation — so that reasoning, work, orchestration, and governance stay in their own domains.

## What the operating model does not do

### It does not perform reasoning
The Operating Model holds no reasoning. When the enterprise needs to think, it routes to Director Intelligence ([reasoning](../director-reasoning/README.md)); the operating model never reasons in that domain's place.

### It does not execute work
The Operating Model performs no tasks and produces no outcomes. When approved work must run, Execution runs it ([execution](../director-execution/README.md)); the operating model only keeps the organization coherent while it does.

### It does not orchestrate execution
The Operating Model does not distribute, schedule, or synchronize running work ([execution orchestration](../execution-orchestration/README.md)). Its rhythm is organizational cadence, not task timing ([organizational rhythm](03-organizational-rhythm.md)).

### It does not redefine governance
The Operating Model runs the existing governance regime continuously; it creates no new regime and alters none ([governance cycle](04-governance-cycle.md), [enterprise governance](../enterprise-organization/06-enterprise-governance.md)). "Governance cycle" is the existing governance in continuous operation, not a redefinition.

### It does not bypass organizational authority
No operating cycle, rhythm beat, or governance pass lets any unit act beyond the Director's authority ([enterprise authority model](../enterprise-organization/04-authority-model.md)). Operation flows through the hierarchy, never around it. Committing actions still rest on Director approval.

### It does not change the structure on its own
The Operating Model preserves structural stability; it does not reshape the hierarchy, reassign seats, or transfer ownership by itself. Structural change is a Director-gated act ([operating lifecycle](02-operating-lifecycle.md)), not a side effect of operating.

### It does not define workflows or business procedures
The Operating Model defines organizational operation, not procedures. Workflows, business processes, cadence procedures, and their runtime are out of scope ([README](README.md)) — later phases behind the Director gate.

## Inputs

- The **operating principles, lifecycle, rhythm, governance cycle, and health** ([01](01-operating-principles.md)–[05](05-organizational-health.md)) — the frame these boundaries protect.

## Outputs

- A **clear negative space** — the set of things the operating model refuses — that keeps reasoning, execution, orchestration, and governance sovereign in their own concerns.

## Boundaries

- This document **adds no capability** — it removes ambiguity about what the operating model is not.
- It **describes no runtime or mechanism** — only the limits of the operating concern.

## Future direction

As the enterprise grows and later phases add workflows, procedures, and runtime, these boundaries hold unchanged. New machinery gains the ability to run *within* the operating model — never the right to make the operating model reason, execute, orchestrate, redefine governance, or bypass authority. The Operating Model stays organizational operation, forever.
