# 04 — Provenance Architecture

## Purpose

Define the constitutional lineage required to understand where Memory came from, how it changed, and who remains attributable.

## Provenance Model

Provenance includes:

- originating source identity and source authority;
- contributing organizational context;
- accountable owner and steward;
- admission basis and admitting authority;
- declared transformations or derivations;
- source and Memory version references;
- classification and Tenant continuity;
- timestamps as record context, not proof of truth;
- Governance qualifications and exceptions;
- supersession, retention, and archive lineage.

## Attribution

Attribution identifies who or what contributed, asserted, transformed, reviewed, or governed information. Attribution does not confer truth, ownership, authority, approval, or liability beyond declared organizational rules.

## Derived Information

A derived Memory Item must cite its inputs, declare the nature of derivation, preserve source limitations, and receive a distinct identity. It must never impersonate a canonical source.

## Rules

- **P20-PROVENANCE-001:** Every admitted Memory Item must trace to an identifiable source or explicitly declared source set.
- **P20-PROVENANCE-002:** Every material transformation must remain visible and attributable.
- **P20-PROVENANCE-003:** Derived Memory must retain distinct identity from source Memory.
- **P20-PROVENANCE-004:** Loss of required provenance invalidates consumption eligibility.
- **P20-PROVENANCE-005:** Provenance records subject to immutable-history obligations must not be rewritten.
- **P20-PROVENANCE-006:** Timestamp, custody, or technical origin must not be treated as truth.

## Enterprise Example

A cross-domain forecast preserves the Sales and Finance source versions, each domain's interpretation, the declared composition, and unresolved disagreement. The composite does not replace either source.
