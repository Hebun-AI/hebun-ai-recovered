## 10. Enrollment artifact semantics

> *"At time T a bearer presenting invitation I submitted an enrollment request. Governance approved it by decision D, or refused it for reason R. It was completed by establishing auth_identity X."*

Four states, each with all-or-nothing CHECK evidence in **both** directions:

```
identity_enrollment_requests_approved_chk
  (status IN ('approved','completed')) = (approved_at ∧ approval_decision_id ∧ actor pair)
identity_enrollment_requests_rejected_chk
  (status = 'rejected')  = (rejected_at ∧ non-empty rejection_reason)
identity_enrollment_requests_completed_chk
  (status = 'completed') = (completed_at ∧ enrolled_auth_identity_id)
identity_enrollment_requests_human_approver_chk
  approved_by_actor_type IS NULL OR = 'human'
```

**A rejection stores no `approval_decision_id`** — the column is named for what it holds, and the CHECK forbids it otherwise. A refusal's Governance decision is found the way every decision is found: by `subject_type` + `subject_id` on `decision_records`. Asserted on a real database.

## 13. Identity authority implementation

`insertLocalIdentity` was added to `identity-repository.server.ts` — **the first product writer Identity authority has ever had**, living in the module that already owns every read of `users` and `auth_identities`.

- Takes a `Pick<ControlPlaneDatabase, "insert">`, so it joins the caller's transaction.
- Writes `status='active'` and `verified_at` **together**, because `auth_identities_active_chk` requires exactly that pair.
- `is_primary = true` — the human's first and only identity.
- Coordinates are constants matched to the seed: `provider='local'`, `issuer='hebun-local'`, `subject='local:<normalized email>'`. Asserted against `scripts/r1-seed.mjs`.
- Leaves uniqueness to the database; a losing race surfaces as `23505` and is mapped to an honest refusal.

`isEmailClaimed` was added alongside it — returns a **boolean**, never a row, so "is this address taken" cannot become an account directory.

**Structurally enforced:** a test walks all of `src/` and asserts that `identity-repository.server.ts` is the **only** file that inserts into `users` or `auth_identities`. I1.2 does not import either table.

## 14. Credential authority implementation

Two minimal, behaviour-preserving changes inside Credential authority:

1. **`insertPasswordCredential`'s handle type widened** from `ControlPlaneDatabase` to `Pick<ControlPlaneDatabase, "insert">`, so it can join a transaction. Same narrowing `writeGovernanceDecisionWithin` already uses. Same statement, same defaults, same index.

2. **`establishFirstPasswordCredential` added** — plaintext in, credential id out. It hashes *and* inserts inside the authority.

> **Why the composition had to move here.** The first implementation hashed in the enrollment module and passed `salt` / `secretHash` across the boundary. `tests/d1-flow/boundaries-and-firewall.ts` caught it: only three files in `src/` may name the stored secret. That firewall was right, and it was not weakened — the composition moved into the authority instead. The enrollment module now never holds derived credential material at all.

**No policy is enforced in Credential authority, deliberately.** `MIN_ENROLLMENT_PASSWORD_LENGTH = 12` is checked at I1.2's own boundary, because the caller is what knows which act is being performed.

## 15. Credential ordering

**Model C, as approved.** The secret arrives only after Governance approval.

```
pending enrollment  →  Governance approval  →  identity created
                    →  first credential submitted  →  hashed + persisted inside Credential authority
                    →  enrollment completed
```

No password or hash is ever stored while waiting for approval, because under Model C none exists: `auth_credentials.auth_identity_id` is NOT NULL and no identity exists before approval. `auth_credential_status` needed no `pending` value.

The scrypt derivation happens **inside** the transaction. That is deliberate and documented: deriving earlier would produce credential material for a ceremony the conditional completion might refuse.

## 17. Rejection semantics

A refusal is terminal and leaves **nothing global** behind:

- `status='rejected'` + `rejected_at` + non-empty `rejection_reason`, CHECK-paired.
- A Governance `reject` decision with outcome `identity-enrollment-rejected`.
- An audit row with `result='rejected'`.
- **No user. No identity. No credential. No session. No membership.**

Proven on a real database: after a refusal, `users` has no row at that address and `auth_identities` has no row at that subject. **The intended human's email slot and local-subject slot are both free** — the exact denial-of-service the Gate B design was built to avoid.

A rejected ceremony is terminal for the invitation too: the partial unique index is `WHERE status <> 'rejected'`, so the slot does **not** reopen. A new attempt needs a new invitation, which is a Governance act.

## 18. Self-approval proof

**Structurally impossible, proven by the absence that causes it.**

1. Before Act 3 the prospective human has no `users` row, no identity and no credential → `findActiveLocalIdentityByEmail` finds nothing → `issueLocalSession` refuses at step 1.
2. After Act 3 they have both — and **no membership** → `issueLocalSession` returns `forbidden("membership")` → no session → `resolveTenantContext()` returns null → `resolveGovernanceAuthority` is unreachable with them as the actor.

Asserted on a real database: the enrolled human has zero memberships, and **even a deliberately fabricated `TenantContext` naming them is refused** with `not-the-governance-authority`, because Governance authority is derived from `decision_records`, not from the context.

**No redundant `actor != subject` constraint was added.** The lifecycle already forbids it three times over.

Adjacent cases tested: an existing human at the invited address is refused at Act 1 with `already-enrolled` — the existing-human path is I2's, and I1.2 declines it rather than creating a duplicate.

## 19. Transaction boundaries

| Act | Contents | Atomic |
|---|---|---|
| **Act 1** | enrollment row insert | one statement |
| **Act 2** | governance session + decision + conditional `pending → approved\|rejected` + audit | **one transaction** |
| **Act 3** | `users` + `auth_identities` + `auth_credentials` + conditional `approved → completed` + audit | **one transaction** |

**Never combined:** Act 1 with Act 2 (two moments, two humans — that is the point of two keys); Act 2 with Act 3 (the approver approves, the bearer completes).

**The required property, proven:** a failure during credential establishment cannot leave a falsely completed enrollment, and cannot leave an active identity with no usable credential. The concurrency test asserts directly that no `auth_identity` exists without a credential — an identity that claimed onboarding succeeded when it had not.

## 20. Concurrency proof

Real PostgreSQL, disposable database, `Promise.all` races.

| Race | Invariant | Result |
|---|---|---|
| two Act 1 submissions, one capability | `…_one_live_per_invitation_uq` (partial) | 1 winner; loser told `enrollment-already-started`; **one** ceremony row; no user, no identity |
| approval racing rejection | conditional `UPDATE … WHERE status='pending' RETURNING id` | exactly 1 authoritative outcome; loser `already-decided` |
| **the loser's rollback** | one transaction | **1** decision, **1** governance session, **1** audit row — no orphans |
| two approvals of one ceremony | same conditional transition | 1 winner; the row names the surviving decision |
| two completions | conditional `WHERE status='approved'` + `users_email_uq` + `auth_identities_provider_issuer_subject_uq` | 1 human, 1 identity, 1 active credential; **zero identities without a credential** |
| completion after completion | same | refused, and still exactly one human at that address |

**No `SELECT → if absent → INSERT` anywhere.** Every invariant is a database constraint or a conditional write, and no constraint outside Gate B was added to make any of it work.

## 29. Firewall proof

`tests/i1-2-flow/boundaries-and-firewall.ts`, 16 sections. Beyond §6 and §28:

- **no second Governance resolver** — the module contains no `activeDelegationsSql`, `bootstrap = true`, or `decision_records` access.
- **no membership / session / role reach** — 10 forbidden tokens, plus an import-level assertion.
- **no dev-credential import** — and `src/` does not reach into `scripts/` at all (existing test, still passing).
- **no mail, SSO, MFA, passkey, recovery, Computer Use, terminal, Knowledge, provider, execution** — 20 module/API names, scanned across the executable surface only.

> The capability scan runs against the **runtime** files, not `contracts.ts`. Its `NON_EFFECTS` list names Computer Use and terminal precisely to state that they do not happen; a scan that treated an honest denial as a violation would push the phase toward hiding its own limits. That reasoning is on disk beside the constant.

## 44. Limitations

1. **A capability stolen before Act 1 still lets the thief be the submitter.** The second key reduces this to a human-in-the-loop check with visibility and a veto. It does not eliminate it, and `TWO_KEY_INVARIANT.deliveryLimitation` says so in the code.
2. **No mail runtime.** Delivery is out of band. `invitations.last_sent_at` and `send_count` remain untouched.
3. **Act 1 has no audit row** — no honest actor exists for it. The enrollment row's `submitted_at` is the evidence.
4. **No product surface.** I1.2 is server functions only; a route and a UI belong to whichever phase makes onboarding reachable.
5. **The enrolled human cannot yet log in usefully** — identity ✅, credential ✅, membership ✗.
6. **A rejected ceremony consumes the invitation.** Retrying requires a new one, which is a Governance act. Deliberate.
7. **The credential half is local-password-specific.** `auth_credential_type` holds one value; the enrollment and verification halves are provider-neutral.
8. **Two tenants inviting the same brand-new human is a race** — the first to complete owns the identity; the second is refused with `already-enrolled` and becomes I2's existing-human path.
